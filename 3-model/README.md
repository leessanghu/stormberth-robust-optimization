# 3. 최적화 모형

태풍이 지나간 뒤 밀린 배를 선석과 크레인에 어떻게 나눠줄지 푸는 단계입니다.
앞 단계에서 실측한 값([`docs/findings.md`](../docs/findings.md))이 여기 입력으로 들어갑니다.

---

## 우리가 하려는 것

태풍이 지나가면 배가 한꺼번에 몰립니다. 부산에서 실제로 하루에 58척까지 들어왔습니다.
이 배들을 **어느 선석에, 몇 번째로, 크레인 몇 대로** 붙일지 정하는 게 이 단계입니다.

어려운 건 **배가 언제 올지 정확히 모른다**는 점입니다.
그래서 "운이 나빠도 크게 망하지 않는" 배정을 찾습니다. 이게 로버스트 최적화입니다.

잘했는지 확인하려면 **비교 대상**이 있어야 합니다. 그래서 다섯 가지를 같이 돌립니다.

| 방법 | 어떤 상황을 상정하는가 | 무엇을 최소화하는가 |
|---|---|---|
| FCFS | 없음 (규칙만) | 없음 |
| nominal | 명목값 1개 | 그 값 |
| SAA | 참 분포에서 뽑은 K개 | 평균 |
| **로버스트** | Γ-예산 불확실성 집합의 꼭짓점 | **최댓값** |
| 완전정보 | 실현값 1개 (`real`) | 그 값 |

**제약은 다섯이 전부 같습니다.** 위 두 열만 다릅니다.

## 지켜야 할 규칙 3개

다섯 방법을 **공정하게** 비교하기 위한 규칙입니다. 하나라도 깨지면 비교가 무의미해집니다.

### ① 시작 시각은 각자 계산하지 않습니다

결정이 두 번 일어납니다.

```
먼저 정하는 것     어느 선석에, 몇 번째로, 크레인 몇 대    <- 각자 정함
나중에 정해지는 것  몇 시에 시작해서 몇 시에 끝나나         <- 공용 코드가 정함
```

**우리가 비교하려는 건 앞의 것**입니다. "누가 배정을 잘했나"를 보려는 거니까요.

그런데 각자 시작 시각까지 계산해서 내면 이렇게 됩니다.

```
FCFS 담당      내 배정 + 내 방식의 시간 계산  ->  1,200시간
로버스트 담당   내 배정 + 내 방식의 시간 계산  ->    900시간
```

300시간 차이가 났는데 **배정이 좋아서인지, 시간 계산 방식이 달라서인지 알 수가 없습니다.**

그래서 시간 계산은 `core/recourse.py` 한 파일이 전담합니다.
그러면 차이의 원인이 배정 하나로 좁혀집니다.

> 시험으로 치면 — 답안은 각자 쓰되 **채점은 한 사람이 같은 기준으로** 하는 겁니다.

### ② 숫자는 `run_all.py` 에서만 나옵니다

각자 자기 노트북에서 돌리면 이렇게 어긋납니다.

```
FCFS   : "1,200시간 나왔어요"    <- 시드 42, 인스턴스 3개
nominal: "1,100시간이요"         <- 시드 7,  인스턴스 5개
```

다른 배를 다른 날씨에서 돌린 거라 비교가 안 됩니다.
`run_all.py` 가 **같은 인스턴스·같은 시나리오·같은 시간제한**으로 전부 돌리고 표를 하나 뱉습니다.
보고서에는 그 표만 씁니다.

### ③ 설정은 `config.yaml` 에만 둡니다

시간제한·시드·Γ·반복수를 자기 코드에 박아두면, 예산을 더 받은 쪽이 당연히 이깁니다.
알고리즘이 좋아서가 아니라요. 전부 `cfg` 에서 읽어 씁니다.

## 도착 과정 — 실측을 어떻게 꽂나

이게 이 연구의 차별점입니다. 기존 robust BAP 는 변동폭을 임의로 잡지만, 여기선 관측값으로 잡습니다.
다만 **DiD 결과는 일별 집계 효과**이고 모형이 필요한 건 **선박별 도착 시각**이라 변환이 필요합니다.

**1단계 — 강도 함수.** DiD 계수를 일별 도착 강도의 배수로 읽습니다.

```
m(D−1)=0.37   m(D0)=0.16   m(D+1)=0.56   m(D+2)=1.08
m(D+3)=1.16   m(D+4)=1.14  m(D+5~)=1.00
                                (m = 1 + 효과%/100)
```

**2단계 — 수준.** 기저 도착률 λ₀ 는 ρ 격자가 정합니다.
실측 일평균 33척은 **항만 전체**값이라 터미널 하나에는 그대로 쓰지 않습니다.
대신 "총 선박 수 n = ρ × 용량 ÷ 척당 작업량"으로 역산하고, 그 n 을 위 강도 비율로 배분합니다.

> **형태는 데이터가, 수준은 격자가 정합니다.** 이 분리가 중요합니다.

**3단계 — 이연과 소멸.** 폐쇄 중 못 온 배가 전부 나중에 오는 게 아닙니다.
누적 분석에서 **반등이 손실의 약 20%만 회복**시켰습니다.

```
폐쇄 중 미도착분 D  →  φ·D 만 재개 후로 이연 (φ ≈ 0.2)
                       나머지는 타 항만으로 이탈하거나 소멸
```

φ 는 민감도 대상입니다. φ=1.0(전부 이연)로 두면 backlog 를 과대평가하게 됩니다.

**4단계 — 불확실성.** 위 과정이 *명목* 시나리오입니다.
로버스트의 불확실성 집합은 여기서 각 선박 도착을 ±`arrival_jitter_h` 안에서 흔들되,
동시에 흔들리는 선박 수를 Γ 개로 제한합니다 (Bertsimas–Sim 예산).

## 자가 점검

`run_all.py` 가 끝나면 이 순서를 자동으로 확인합니다.

```
완전정보(WS) ≤ SAA(RP) ≤ nominal(EEV)      (평균 기준)
```

**이건 정리입니다** (Birge & Louveaux). 깨지면 어딘가 코드가 틀린 겁니다.

- `nominal ≤ FCFS` 는 **정리가 아닙니다.** 깨져도 버그가 아닙니다.
- `로버스트 vs SAA` 도 순서가 없습니다. 최악 기준과 평균 기준이 다른 답을 줍니다.
  그 거래(price of robustness)를 보고하는 게 이 연구의 논점입니다.

**완전정보를 "절대 하한"이라고 쓰면 안 됩니다.** 2단계가 고정 규칙이므로,
여기서 말하는 완전정보는 *"실현값을 다 알고 1단계를 최적으로 골랐을 때, 그 규칙 하의 최선"* 입니다.
규칙 자체가 최적이 아니므로 진짜 최적해는 이보다 낮을 수 있습니다.
순서 점검은 세 방법이 같은 규칙을 쓰므로 그대로 유효합니다.

## 실험 설계

**격자 (주 결과)** — 혼잡도 × 폐쇄시간

```
ρ          0.60 / 0.75 / 0.90      가동률 = 해야 할 크레인·시간 / 쓸 수 있는 크레인·시간
t_close    12h / 24h / 48h         용량-반응 3등급 (실측)
```

9칸 × 실현 20개 × 방법 5개 = 900회.

**에피소드 (사례 연구)** — 실제 태풍 5개 조건을 재현

```
2019 타파 / 2020 마이삭+하이선 / 2021 오마이스+찬투 / 2022 힌남노 / 2023 카눈
```

재현한 인스턴스이지 실제 운영 기록이 아닙니다.
"실제보다 나았다"가 아니라 **"같은 조건에서 FCFS보다 나았다"** 까지만 주장합니다.
